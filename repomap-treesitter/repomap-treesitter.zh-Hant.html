用 tree-sitter 打造更好的儲存庫地圖（Building a better repository map with tree sitter）

2023 年 10 月 22 日

GPT-4 在「自成一體」的程式任務上非常有用，例如產生或修改一個沒有相依性的簡單函式。GitHub CoPilot 這類工具很擅長處理這種單純的程式任務。

但在既有的較大型程式碼庫裡做複雜的修改，對人和 AI 都困難得多。想順利完成，你得做到三件事：

  1. 找出需要修改的程式碼。
  2. 理解這段程式碼與程式碼庫其餘部分之間的關係。
  3. 正確修改程式碼，完成任務。

只要告訴 GPT 哪些檔案需要改（1），再讓它看看這些檔案怎麼融入程式碼庫的其他部分（2），GPT 其實很擅長改程式碼（3）。

本文聚焦第（2）步，也就是提供「程式脈絡」（code context）：

  • 我們得幫 GPT 理解整個程式碼庫。
  • 這能幫它理解自己需要修改的程式碼，因為這些程式碼可能相依於程式碼庫的其他部分。
  • 這也能幫 GPT 在寫新程式碼、改既有程式碼時，尊重並運用程式碼庫其他地方既有的函式庫、模組與抽象層。
  • 我們必須用有效率的方式，把這些「程式脈絡」全部傳達給 GPT，讓它塞得進有限的脈絡視窗（context window）。

為了解決這些問題，aider 會送給 GPT 一份整個 git 儲存庫（repository）的簡明地圖，裡頭包含最重要的類別與函式，以及各自的型別與呼叫簽名。

這份儲存庫地圖（repository map）現在改用 tree-sitter 自動建立，從原始檔中擷取符號定義。許多 IDE、編輯器與 LSP 伺服器都用 tree-sitter 幫人類搜尋、瀏覽大型程式碼庫。Aider 現在用它幫 GPT 更了解、更容易瀏覽與編輯較大型儲存庫裡的程式碼。

想用本文談到的技巧搭配 GPT-4 寫程式，只要安裝 aider 即可。

問題所在：程式脈絡（The problem: code context）

GPT-4 很擅長「自成一體」的程式任務，例如撰寫或修改一個沒有外部相依性的純函式。像「寫一個 Fibonacci 函式」或「用 list comprehension 改寫這個迴圈」這類要求，GPT 應付起來輕鬆，因為它們除了正在討論的那段程式碼之外，不需要任何脈絡。

真實的程式碼大多不純粹、不自成一體，而是和儲存庫裡許多不同檔案的程式碼互相交纏、彼此相依。假如你要 GPT「把 Foo 類別裡所有的 print 陳述式改成使用 BarLog 日誌系統」，它需要看到並修改 Foo 類別裡的程式碼，但同時也得知道專案的 BarLog 子系統該怎麼用。

簡單的做法是把整個程式碼庫連同每次修改要求一起送給 GPT。這樣 GPT 就有全部脈絡了。但即使是中等大小的儲存庫也辦不到，因為塞不進脈絡視窗。

比較好的做法是有選擇性地挑出要送的檔案。以上面的例子來說，你可以送出含有 Foo 類別的檔案，以及含有 BarLog 日誌子系統的檔案。這招效果不差，aider 也支援：你可以手動指定要把哪些檔案「加進聊天」。

但送整個檔案來傳達程式脈絡太笨重，浪費了珍貴的脈絡視窗。GPT 不需要看到 BarLog 的完整實作，只要了解得足以使用它就好。只為了傳達脈絡而送出整份程式碼檔案，很可能一下子就把脈絡視窗用光。

Aider 也努力減少用 AI 寫程式時的手動工作。所以在理想世界裡，我們希望 aider 能自動找出並提供所需的程式脈絡。

用儲存庫地圖提供脈絡（Using a repo map to provide context）

使用者一提出修改要求，aider 就會連同一份儲存庫地圖（repo map）一起送給 GPT。地圖裡有儲存庫中的檔案清單，以及每個檔案裡定義的關鍵符號。它藉由納入每個定義的關鍵程式碼行，呈現這些符號在原始碼中怎麼定義。

下面是 aider 儲存庫地圖的一小段範例，只顯示 base_coder.py 與 commands.py 的地圖：

aider/coders/base_coder.py:
⋮...
│class Coder:
│    abs_fnames = None
⋮...
│    @classmethod
│    def create(
│        self,
│        main_model,
│        edit_format,
│        io,
│        skip_model_availabily_check=False,
│        **kwargs,
⋮...
│    def abs_root_path(self, path):
⋮...
│    def run(self, with_message=None):
⋮...

aider/commands.py:
⋮...
│class Commands:
│    voice = None
│
⋮...
│    def get_commands(self):
⋮...
│    def get_command_completions(self, cmd_name, partial):
⋮...
│    def run(self, inp):
⋮...

這樣把儲存庫畫成地圖，帶來幾個重要好處：

  • GPT 能看到儲存庫各處的類別、方法與函式簽名。光是這樣，可能就足以讓它解決許多任務。例如，只靠地圖上顯示的細節，它大概就能想出怎麼使用某個模組匯出的 API。
  • 如果需要看更多程式碼，GPT 可以用地圖自己判斷該進一步查看哪些檔案。接著它會要求看這些特定檔案，aider 就會自動把它們加進聊天脈絡。

最佳化地圖（Optimizing the map）

當然，對大型儲存庫來說，光是一份儲存庫地圖可能就超過 GPT 的脈絡視窗。Aider 的解法是只送地圖中最相關的部分。做法是用圖排序演算法分析完整地圖：每個原始檔是一個節點，有相依關係的檔案之間連上邊。分析完，aider 再挑出程式碼庫裡最重要的部分，塞進使用者指定的 token 預算（透過 --map-tokens 參數設定，預設為 1k token），藉此最佳化儲存庫地圖。

上面那張範例地圖並沒有包含那些檔案的每一個類別、方法與函式。它只納入最重要的識別字，也就是程式碼其他部分引用最頻繁的那些。這些正是 GPT 理解整個程式碼庫所需的關鍵脈絡。

用 tree-sitter 製作地圖（Using tree-sitter to make the map）

底層實作上，aider 用 tree sitter 建立這份地圖。具體來說是使用 py-tree-sitter-languages python 模組，它為大多數熱門程式語言提供簡單、可用 pip 安裝的 binary wheel。

Tree-sitter 依程式語言的語法把原始碼解析成抽象語法樹（Abstract Syntax Tree，AST）。有了 AST，我們就能辨識函式、類別、變數、型別與其他定義在原始碼裡的什麼位置，也能找出這些東西在程式碼其他地方使用與引用的位置。

Aider 用這些定義與引用判斷儲存庫裡哪些識別字最重要，並產出只顯示那些關鍵程式碼行的儲存庫地圖。

那 ctags 呢？（What about ctags?）

tree-sitter 版儲存庫地圖取代了 aider 最初使用的 ctags 版地圖。從 ctags 換到 tree-sitter 帶來不少好處：

  • 地圖更豐富，直接從原始檔顯示完整的函式呼叫簽名與其他細節。
  • 靠著 py-tree-sitter-languages，我們透過一個 python 套件就能完整支援許多程式語言，而這個套件在一般的 python -m pip install -U aider-chat 過程中會自動安裝。
  • 使用者不必再透過外部工具或套件管理器（brew、apt、choco 等）手動安裝 universal-ctags。
  • tree-sitter 整合是 aider 未來工作與功能的關鍵推手。

未來工作（Future work）

還記得我們點出用 GPT 在既有的較大型程式碼庫裡完成程式任務所需的 3 個關鍵步驟：

  1. 找出需要修改的程式碼。
  2. 理解這段程式碼與程式碼庫其餘部分之間的關係。
  3. 正確修改程式碼，完成任務。

我們現在用 tree-sitter 幫忙解決程式脈絡問題（2），但它也是未來工作的關鍵基礎，用來自動找出所有需要修改的程式碼（1）。

目前 aider 仍仰賴使用者指定哪些原始檔需要修改才能完成要求。使用者用 aider 的 /add 指令手動「把檔案加進聊天」，讓 GPT 能修改這些檔案。

這方法行得通，但未來的一項重點工作，是運用 GPT 與 tree-sitter 的力量，自動辨識程式碼的哪些部分需要修改。
