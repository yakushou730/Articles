自我改進的程式編寫代理（Self-Improving Coding Agents）

2026 年 1 月 31 日

想像你結束一天的工作，隔天醒來，新功能已經寫好、測試完成，等著你審查。這是自主 AI 編碼代理（autonomous AI coding agents）的承諾：用 Claude Code 這類工具跑連續迴路（continuous loops），在你睡覺時持續改進並交付程式碼。

這篇文章要談怎麼建立這類自我改進的代理迴路（self-improving agent loops），從編排迴路、組織脈絡檔案，一路講到記憶持久化、QA 驗證、規模化、除錯與風險管理。希望其中有些內容對其他人有幫助。

本文是對 Ryan Carson 那篇優秀的 How to make your agent learn and ship while you sleep 的補充，我高度推薦一讀。我們最近在晚餐時聊了不少代理式編碼（agentic coding）的未來，我想把他提到的部分技巧再延伸一些。

「連續編碼迴路」（The “continuous coding loop”，Ralph Wiggum 技巧）

這套方法的核心是一個迭代式的代理迴路（agent loop），常被暱稱為「Ralph Wiggum」技巧（由 Geoffrey Huntley 與 Ryan Carson 等人推廣）。關鍵想法是把開發拆成許多小任務，讓 AI 代理在迴路中一次處理一個。

每次迭代都走一個循環（cycle）：

  1. 挑下一個任務：從待辦清單（例如任務的 JSON）挑出還沒完成的一項。
  2. 實作任務：代理針對該功能或修正撰寫、修改程式碼。
  3. 驗證變更：為這個任務跑測試、型別檢查或其他品質檢查。
  4. 提交程式碼：檢查通過就提交，把變更整合進程式庫。
  5. 更新任務狀態：標記為完成，並記下學到的事。
  6. 重設代理脈絡：接著處理下一個任務，直到所有任務完成或觸發停止條件。

每次迭代都重設記憶，代理就不會累積混淆，能保持專注。這種「無狀態但迭代」的設計是可靠性的關鍵，它解決了脈絡溢出的問題，也就是叫 AI 一次做完一整個功能時常碰上的毛病。

不用一個巨大提示（prompt）讓模型跑偏或忘掉細節，代理每個回合只拿到一份全新、範圍受限的提示，對應單一且定義明確的任務。

結果是程式碼更乾淨、幻覺更少，因為每次執行都從空白狀態與明確指示開始。

在這裡，代理會不斷挑任務、寫程式、跑測試、更新任務清單，直到所有任務都通過。

任務要小，標準要明確

把工作拆成原子化的使用者故事（atomic user stories）或任務很重要。每個任務都要小到能在一次 AI 工作階段內完成，而且通過／不通過的標準不能有模糊空間。

舉例來說，不要寫「建立整個儀表板」，而是拆成「加一個導覽列，連到 Home、About、Contact」，並在驗收標準裡寫明具體期望（例如「目前頁面的連結以藍色標示」）。

拆到這種粒度，代理才知道每一步的「完成」長什麼樣。它也降低代理走偏的機率：任務沒通過測試或標準，迴路立刻就能抓到並修正方向。

實作要點：先定義 SPEC，再轉成任務 JSON。先為功能寫一份清楚的規格，邊界情況可以借助 AI 補齊。

接著把它轉成結構化任務清單（例如 prd.json），納入所有小型使用者故事與驗收標準。Carson 為 Amp／Claude 寫的 /prd 與 /tasks skill 可以自動完成這個轉換。

產出是一份機器可讀的待辦清單，交由代理迴路逐步執行。

編排迴路

跑迴路用一支簡單腳本就行。在 Carson 的實作裡，這確實就只是一支 Bash 腳本或 Python 腳本（例如 ralph.sh），反覆用提示模板呼叫 AI 代理。用 Amp 或 Claude Code，也可以靠 CLI 指令或外掛達成同樣效果。例如用 Amp 的 CLI，可以跑像這樣的虛擬碼迴路：

while :; do  
   amp run \-s prompt.md \-o progress.txt  \# Run Amp with the prompt, save output  
   if grep \-q "\<promise\>COMPLETE\</promise\>" progress.txt; then break; fi  
done

實務上，迴路腳本會載入任務清單、挑下一個未完成的任務、組出提示（包含相關程式檔與準則等脈絡），然後呼叫 AI 模型。模型回應指出成功或失敗後，腳本負責套用程式碼變更、跑測試。整個過程重複到所有任務完成，或達到最大迭代次數為止。

重點是每次迭代彼此隔離：代理每次都重新啟動，通常是新的 Claude 或 GPT 行程，等於真的把狀態清空，再重新餵進必要的脈絡。

複合迴路（Compound loops）：除了單一任務序列，進階工作流會編排多個階段的迴路。

舉例來說，Compound Product 是一套開源系統，先跑分析迴路（Analysis loop）（讓 AI 讀每日報告，判斷該做什麼），再跑規劃迴路（Planning loop）（產生 PRD 與任務），最後跑執行迴路（Execution loop）（由編碼代理實作任務）。這條複合流程讓代理不只寫功能，也決定最高優先的功能是什麼。

不是每個專案都需要這種程度的自動化，但它示範了迴路怎麼串起來：一個代理的輸出（例如任務清單或分支名稱）成為另一個代理的輸入，構成更大的持續交付系統。

脈絡與記憶的最佳實務：AGENTS.md 手冊

這類代理迴路最有力的機制之一，是使用持久的脈絡檔案（context files），讓知識在迭代之間延續。

與其硬要單一 AI 工作階段記住所有事（超過脈絡視窗就辦不到），我們把重要資訊明確寫進磁碟，讓它能在未來的提示裡重新注入。主要檔案通常命名為 AGENTS.md（也有人用 MEMORY.md 之類的名字）。

AGENTS.md 是什麼？它基本上是代理的隨身筆記本，記下代理的發現、專案慣例，以及任何你希望未來所有代理都知道的指引。

每完成一個任務，迴路可以追加關鍵學習，例如「注意：這個程式庫用 Library X 處理 Y，請沿用這個模式」，或「坑：每次更新 user model 時，也要更新 audit log」。

久而久之，這會變成一座提示寶庫，讓代理不再重複過去的錯誤。在 Carson 的 Compound Product 哲學裡，「代理會更新 AGENTS.md，把發現的模式記錄下來供未來迭代使用」。這表示每次改進都真的讓下一次改進更容易，因為代理累積出一套知識庫，知道這個程式庫長什麼樣、該怎麼跟它打交道。

組織知識庫：把 AGENTS.md 分成幾個區塊，讓人與 AI 都好讀。例如：

  • 模式與慣例（Patterns & Conventions）：高階模式（例如「本專案使用 SSR，UI 元件放在 /components，API 放在 /routes」）。
  • 坑（Gotchas）：曾讓代理或開發者栽跟頭的事（「新增 enum 時要更新 constants.ts，否則測試會失敗」）。
  • 風格／偏好（Style/Preferences）：程式風格筆記（「依照設定遵循 ESLint 規則；優先用函式元件而非 class」、「測試用 pytest fixture，跟現有測試一致」）。
  • 近期學習／變更（Recent Learnings/Changes）：近期問題的摘要，以及怎麼解決的。

條目要簡短、就事論事，它們是提示的添加物（prompt additives），用來引導模型。許多 AI 編碼工具（Claude Code、Cursor、Amp）只要看到 AGENTS.md 或 README.md 這類檔案，就會自動把它們納入提示脈絡。例如 Amp 在代理開始新一輪迭代時，會掃描儲存庫並把 AGENTS.md 內容拉進來，給模型專案的背景。

脈絡注入策略：留意脈絡大小。知識檔案變大之後，未必每個任務都值得注入全部內容（脈絡膨脹會拖慢效能，或讓模型忽略指示）。

好習慣是讓 AGENTS.md 保持聚焦、隨時更新，過時的資訊就封存到另一個檔案。有些進階做法會用檢索：把 AGENTS.md 拆成多個主題檔，只放進跟當前任務相關的區塊。但簡單一點的做法通常就夠了：把檔案修剪到只剩最相關的提示，隨著專案慢慢長大。

使用範例：假設你發現代理試著用一個過時的 API。

你可以停掉迴路，在 AGENTS.md 加一條註記：

「v1/users 端點已棄用；請改用 v2/users。」

下次代理處理相關任務時就會看到這條註記，避開已棄用的 API。你也可以直接叫代理自己做這件事：

「不對，別用舊端點。改用新的 v2/users API，把這件事記進 AGENTS.md，然後繼續。」

這個即時回饋技巧由開發者 Eric J. Ma 提出，用來「建立一份持久的偏好記錄，改善代理未來的行為」。

代理會乖乖把修正追加到 AGENTS.md，然後帶著新指示繼續做事，等於從錯誤中學了一課。

最後，可以考慮讓 AGENTS.md 的知識在代理或執行之間共享。如果你跑多條迴路（不同專案或平行任務），可以把一部分共通知識集中管理。Eric Ma 的 MCP（Model Context Protocol）server 就是一個例子，用統一的方式儲存並提供這類脈絡給不同代理。講得更簡單一點：如果你有多個自主代理協同工作，即使只是一個共用 wiki 或一組所有代理工作階段都會參考的 markdown 檔，也能確保一致性。

記憶持久化與複合學習策略

除了 AGENTS.md，穩健的代理迴路還會用幾種持久化機制（persistence mechanisms）保存狀態，避免迭代之間健忘。Carson 的 Ralph 迴路實作在每次執行之間至少用了四種記憶管道：

  • Git 提交歷史（Git Commit History）：每次迭代的程式碼變更都會提交，所以下一輪可以跑 git diff 或檢查儲存庫，看看改了什麼。這樣代理不必回想先前的程式碼，直接從儲存庫讀就好。提交訊息本身也能提供脈絡（「Iteration 5: Added navbar component」）。Amp 或 Cursor 這類工具允許代理自主執行 git log 或 git diff（在權限允許下），從版本控制取得脈絡。
  • 進度日誌（Progress Log，progress.txt）：每個循環追加的純文字日誌，記錄發生什麼事，例如嘗試了哪個任務、通過還是失敗，以及任何錯誤訊息或發現。這是一份按時間排序的記憶。迴路停住或你需要除錯時，翻 progress.txt 就知道哪裡出了問題。也可以叫代理在迭代開始時讀 progress.txt（或其中相關段落），回想先前試過什麼。就把它當成代理的日誌。
  • 任務狀態（Task State，prd.json 或任務清單）：任務的 JSON 檔會隨任務標記完成、passes: true/false 欄位切換而更新。這個檔案保存每項需求的狀態。代理崩潰重啟後，載入 prd.json 就知道還剩哪些任務。代理迴路腳本會跳過已完成的任務，專注在待辦項目，避免重工，也讓人看得出進度。
  • 代理知識（Agents’ Knowledge，AGENTS.md）：如前述，這是長期語意記憶，過去每次執行累積下來的經驗。

這些合起來形成一個複合學習迴路（compound learning loop）：代理並不是機器學習意義上的「線上學習」，但它系統性地記錄結果，讓下一輪迭代（甚至下一個專案！）能受益。

代理想通的每個修正或模式，都會滾進下一次的脈絡。正如 Compound Product 的 README 所說，其哲學是每次改進都應該讓未來的改進更容易。

迭代數十次之後，代理的效益真的可能上升，因為它不再重複犯錯，也會遵循學到的慣例。

還有一些以外掛為基礎的記憶擴充可以運用。

例如 Claude Code 支援「skill」乃至市集外掛，你可以想像（或自己寫）一個 skill，自動保存每次編碼工作階段的摘要，下次載入。Amp 的自動交接（auto-handoff）功能實際上就是短期記憶：當脈絡視窗快要溢出，它可以把對話交接給新的工作階段，附上至今的濃縮摘要。這能避免任務中途流失脈絡，對超大任務或複雜重構很有用。

在更實驗性的做法裡，開發者用向量資料庫（vector databases）儲存與檢索記憶。例如每次迭代後，把 diff 或錯誤訊息做 embedding，連同描述存成向量。新一輪開始前，查資料庫找相似的過去案例，提供給代理。

這有助於辨認出像是「喔，我之前看過這種失敗的測試，當時是這樣修的」。不過這類做法增加複雜度，只要你認真維護代理能直接讀取的簡單產物（檔案與日誌），未必需要。

提示：不管你用哪種持久化方式，都要定期確認代理真的有在用。記憶檔案只有在未來執行時被注入提示才有用。

檢查你的提示模板或代理設定，確認 AGENTS.md 與近期的 progress.txt 條目都包含在內。在 Amp 與 Claude 裡，progress.txt 這類檔案預設可能不會自動載入，所以你可以改提示，寫上「以下是前幾次執行的筆記：」再把內容附進去。

Carson 的做法鼓勵你為專案自訂提示模板（例如 prompt.md 或 CLAUDE.md），可以加入載入專案特定脈絡的區塊，或強調特定指示。

品質保證：測試與驗證迴路

想讓自主代理穩定產出可用的程式碼，自動化驗證是首要條件。少了檢查，代理可能在自以為成功的同時，開開心心地引入 bug 或弄壞建置。穩健的代理迴路會把測試與其他驗證當成循環中的一等公民：

  • 單元與整合測試（Unit and Integration Tests）：有紮實的測試套件，成果會改善很多。代理可以在實作完任務後跑 npm test 或 pytest。測試失敗，迴路就知道任務其實沒完成，可以叫代理修。理想上 prd.json 裡每個使用者故事至少對應一個測試，無論是驗收標準的一部分，或放在儲存庫的測試檔裡。有些系統更進一步，例如要求代理先寫測試再寫程式（測試驅動風格），或對 App 的 UI 狀態做快照以供比對。但最低要求是每次迭代都跑現有測試。
  • 型別檢查與 Lint（Type Checking and Linting）：靜態分析工具（MyPy、tsc 這類型別檢查器，ESLint／Flake8 這類 linter）是很好的自動化回饋，很快就能抓到錯誤。可以把它們排進迴路提交程式碼前的品質檢查。例如在 config.json 設定代理寫完程式碼後執行 npm run typecheck && npm run lint，只有成功結束才繼續。這能避免代理一錯再錯。
  • 迴路中的持續整合（Continuous Integration，CI）：有些進階做法甚至串進 CI 流程。例如 Cursor 的多代理實驗裡有一個「judge」代理來判斷專案是否完成，其中可能包括確認 GitHub Actions CI 是綠燈。在較簡單的單代理迴路裡，你可以在本地跑建置腳本或任何 CI 檢查來模擬。遇到紅旗就該停下：檢查失敗時，代理要去處理（或把任務標為仍失敗，卡住 N 次後可能換下一個）。
  • AI 自我評估（選用）：遇到不容易寫自動化測試的情況（例如沒有測試框架的 UI 變更），可以讓代理自己驗證。例如 Carson 的代理在處理前端任務時會用 dev-browser skill：代理起一個無頭瀏覽器，前往頁面，確認某個 UI 元素存在或某個互動有效。這基本上就是代理驅動的整合測試。驗證失敗，代理就知道要重試。這招很有力，但要確保沙箱機制到位（後面會再談安全），因為這代表代理在執行程式碼、操控瀏覽器。

專家見解：要怎麼讓 AI 代理一開始就寫出好測試？Simon Willison 認為最好的方式是以身作則：在程式庫裡維護高品質測試，代理自然會模仿這些模式。以 LLM 為基礎的程式編寫者傾向遵循眼前看到的風格。如果你的儲存庫裡既有元件都有清楚、簡單的測試，你要求代理加新功能時，它通常也會為新程式碼產出類似的測試。

Willison 指出，專案一旦有乾淨的測試，「代理新增的測試品質往往會與之一致」。他也建議主動叫代理參考已知的良好範例，例如「測試風格請比照 [某個檔案]」，甚至叫它複製另一個儲存庫來看某些模式。這種脈絡播種能大幅改善代理的輸出，也減少日後修爛測試的時間。

實務上，你未必總放心讓代理從零寫測試，很多開發者偏好自己寫、至少自己審。但即使如此，在迴路裡跑那些測試仍然必要。它形成一個回饋迴路：只有程式碼真正符合規格時，代理才算「認為」自己做完了，而測試通過就是這件事的判斷依據。這個代理式 QA 迴路，是把天真的「生一些程式碼」流程變成可靠工程工作流的關鍵。

規模化：並行代理與多迴路編排

到目前為止，我們談的都是一個代理序列處理一份任務清單。如果你想快一點，同時處理多個任務甚至多個專案呢？這個領域近期的實驗已經試過同時跑數十甚至數百個代理。

這還很前沿，日常開發中並不常見，但對於理解這類迴路的規模極限與可能性很有啟發。

並行代理的挑戰：天真地在同一個儲存庫上跑很多代理，就會碰到協調與衝突問題。例如兩個代理可能挑到同一任務，或其中一個改了程式碼，弄壞另一個正在做的事。早期嘗試用共用檔案鎖機制，結果代理會卡住，或把時間浪費在等彼此。它們也可能變得風險趨避，每個只敢做小幅、安全的變更，避開大型複雜任務，因為在這種自由混戰的系統裡，沒有哪個代理覺得自己「該負責」難的部分。

規劃者－工作者模型（Planner-Worker model）：更成功的模式是在代理之間引入階層或分工。例如 Cursor 的 Wilson Lin 描述在一個群集（swarm）裡使用規劃者代理（Planner agents）與工作者代理（Worker agents）。規劃者像專案經理：讀完整個程式庫，決定要做什麼，並產生任務（甚至遞迴地建立子任務）。工作者接著接下這些任務去實作，不用操心全局。

迭代結束時，由一個 Judge 代理評估目標（例如完成專案）是否達成。這個做法避免了漫無目的的遊蕩，吞吐量也大幅提升：Cursor 團隊讓數百個代理協同工作打造一個網頁瀏覽器，一週內在 1,000 多個檔案中產出超過一百萬行程式碼。

你大概不需要這種規模，但你可以為了不同目的平行跑多條迴路。例如一條代理迴路專做前端任務，另一條同時做後端任務（分別在不同部分的程式庫或不同分支上運作）。

真要這麼做，就把工作清楚切分，盡量減少衝突。

另一種情境是為不同的功能分支跑各自的夜間迴路：假設排了 10 個功能，你就對 10 個分支開 10 個代理行程。Ryan Carson 預測，創辦人終究會每晚跑 10 條以上這樣的迴路來加速開發。每條迴路仍遵循同樣的原則，但你需要良好的 CI 實務來整合所有產出（就像同時有多位真人工程師在工作一樣）。

協調工具：如果多個代理非得碰同一個專案，可以考慮用協調檔案或簡單的 API 溝通。共用一份帶鎖機制的 tasks.json 是一種做法（但如前述，檔案鎖並不簡單）。另一種輕量做法是用一支「交通警察」腳本，透過佇列把任務分配給代理。

市面上也開始出現處理多代理工作流的編排平台，但現在多半是自製或研究專案，而不是現成可用的方案。

對今天多數進階使用者來說，規模化指的是往深處迭代，而不是單純往寬處鋪開。讓一個能力夠強的代理迴路在複雜專案上跑更久（整晚或好幾天），通常比開一個難以管理的 swarm 更有成果。模型能力提升之後，長時間執行的單一代理也在進步。

監控、除錯與回饋量測

把寫程式交給自主代理，你就需要看得到它在做什麼。把代理當成真的工程師，它的工作你要審查。以下是監控與除錯代理迴路的一些最佳實務：

  • 即時日誌（Live Logs）：開一個終端機即時追蹤代理輸出或 progress.txt 日誌。迴路應該印出它正在處理哪個任務，你也要能看到測試結果或錯誤。如果發現代理在同一個錯誤上反覆打轉，它可能卡住了，你可以介入（停掉它或給個提示）。很多框架讓你看得到 AI 的訊息，例如 Claude Code 桌面 App 會在代理工作時顯示對話串，Amp 的 CLI 會逐步印出模型輸出。
  • 檢查點提交（Checkpoint Commits）：既然每次迭代都提交到 git，你就有一份很好的稽核軌跡。經常使用 git log 和 git diff。一行 git log --oneline -5 就能看到代理最近幾次提交。diff 裡有哪裡不對，你可以在它跑太遠之前抓到。你甚至可以自動化 diff 審查：例如 diff 比預期大很多，或動到任務範圍外的關鍵檔案（代表代理可能「走偏了」），就中止迴路。
  • 檢查指令（Inspection Commands）：把一些除錯指令放進迴路，或讓它們容易執行。例如用腳本顯示所有任務狀態（jq ‘.tasks[] | {id, story, passes}’ prd.json）就能快速掌握進度。在 progress.txt 裡找「ERROR」或讀最後 N 行，可以知道某個任務為何失敗。
  • 代理內省（Agent Introspection）：有需要時可以叫代理解釋自己。例如它卡在某個任務，你可以改提示寫「如果測試重試 3 次仍失敗，輸出你的推理與計畫。」這能讓代理內部的思維鏈（chain-of-thought）浮現（即所謂的「自我反思」），或許能提供線索。但要節制使用：太多內省也會弄亂迴路，不過它仍是除錯工具箱裡的工具。
  • 效能指標（Performance Metrics）：記錄每次迭代花多久、用了多少成本（API token）很有用。你可以讓迴路記錄每個任務與整體的耗時。如果某個任務花的時間是其他的 10 倍，那代表它很複雜或卡住了。累積很多個晚上之後，你可以蒐集「每小時幾個功能」這類統計，用來判斷某次升級（換模型、調提示）有沒有差別。
  • 自動停止條件（Automated Stop Conditions）：有時候事情會出錯，例如代理陷入徒勞的迴圈（也許碰上解不開的難纏 bug），或外部相依服務掛掉讓測試一直失敗。除了正常的完成條件，也要設定停止條件。最簡單的是最大迭代次數上限，例如跑 50 圈就停，即使還沒做完。這能避免成本失控與無限迴圈。你也可以設定時間上限（「跑超過 3 小時就砍掉」）或閒置條件（「連續 5 次迭代都沒有新提交就跳出」）。這些能確保你回來時看到的是停滯的代理，而不是白跑一整晚。
  • 人工覆寫（Manual Overrides）：即使自動化程度再高，關鍵時刻還是要保留人為介入。一個好模式是讓代理最後開一個pull request，而不是自動合併。這樣你每天早上都能做最後的程式碼審查。測試漏掉的東西（邏輯問題，或只符合驗收標準字面、不符其精神的做法）通常都會被你抓到。這個「真人 QA」步驟目前仍然無可取代：它讓你放心把粗活交給代理，但最終控制權不放。

如果代理某類任務老是失敗，把它當成回饋。也許你的驗收標準太模糊或太嚴；也許代理需要 AGENTS.md 裡對某個框架更好的提示。把失敗當成給你自己、也給代理的學習訊號。

例如代理因為缺少脈絡而搞不定某個第三方 API，可以考慮下次在 AGENTS.md 或程式碼註解裡加一段簡短的使用範例。經過幾天、幾週，這種反思式改進（有點像結對程式設計的回顧）會讓系統更穩健。

風險管理與防護措施

讓會寫程式的代理擁有提交權與 shell 執行權，威力強大，風險也高。你必須刻意管理這些風險。以下是幾個關鍵面向與應對方式：

防止破壞性動作

自主代理一旦設定錯誤，可能刪檔、弄壞儲存庫，或推送不安全的程式碼。降低風險的方法：

  • 限制範圍（Limited Scope）：讓代理在功能分支或 fork 上跑，絕不直接在 main 上。這樣就算它做出離譜的事，審查前正式程式碼都不會被動到。
  • 唯讀與寫入權限（Read-Only vs Write Permissions）：多數代理平台對危險操作都有確認關卡。Amp 與 Claude Code 有 --dangerously-allow-all 這類旗標，讓自動化時跳過確認。

這些旗標要謹慎使用。比較安全的做法是只自動核准唯讀指令，寫入一律人工核准。例如允許代理不用問就跑 grep、git log 或 npm test，但不准未經你明確同意就 git push 或 rm -rf。把安全操作列入白名單，代理就能自由蒐集資訊，副作用仍受控。

  • 沙箱（Sandboxing）：最理想是在受控環境裡跑代理，例如 Docker 容器或 VM，尤其它又有能力執行程式碼（跑測試通常就需要）。

這能限制任何意外指令造成的損害。API key 也要用最小範圍：如果代理需要 API key 去發一則 GitHub 留言，就給它一個只能做這件事、其他都不能的 token。

  • 緊急停止（Emergency Stop）：永遠要知道怎麼在執行中途殺掉代理。可能只是在終端機按 Ctrl+C，或在代理 UI 下特定指令（Claude Code 用 Escape 鍵停止生成）。

看到它在做有害的事，先終止再說，問題之後再問。也可以考慮監控資源使用：代理行程若吃掉異常高的 CPU 或記憶體（可能因為在程式碼裡觸發了瘋狂的無限迴圈），自動監控程式可以把它砍掉。

處理幻覺與偏離

AI 模型有時會產出語法上說得通、語意上卻錯誤的輸出（幻覺（hallucinations））。在寫程式的情境裡，這可能是呼叫不存在的函式、用錯演算法，或寫出毫無意義的註解。還有任務偏離（task divergence）的風險：代理誤解需求，把東西做錯。

應對方式：

  • 規格與提示要夠強（Strong Specs and Prompts）：清楚的驗收標準與定義明確的任務是第一道防線。如果任務寫「POST 到 /api/login 並取得 200 OK」，代理沒什麼空間去幻想出另一個端點。模糊是敵人。事前花時間讓任務毫無歧義，並在提示模板裡明確寫出該做什麼、不該做什麼（系統提示或前言可以列舉「除非指定，否則不要引入任何新相依套件」，或「遵循本儲存庫的程式風格」）。
  • 用驗證抓幻覺（Validation to Catch Hallucinations）：前述的測試與型別檢查會抓到很多幻覺產物（例如呼叫未定義的函式）。型別錯誤、參考錯誤、測試失敗，這些都是代理做了一件不真實的事的訊號。迴路邏輯接著要叫代理修正。很多時候，只要執行程式碼並把錯誤輸出餵回去，模型就足以意識到錯誤並修正。
  • 定期重新聚焦（Periodic Refocusing）：長時間執行的迴路會隨時間偏離，也許一個小誤解就層層累積。對抗偏離的一種技巧是定期用全新的規劃重新開始。例如跑完一定數量的任務後暫停，重跑 /prd skill 或重新掃描程式庫，確認剩下的任務仍然有效。Carson 的團隊提到在非常長時間的代理執行中需要「定期重新開始，以對抗偏離與隧道視野」。實務上，這代表代理完成一大塊之後就讓它停下來，審視中途成果，必要時更新任務清單，然後再繼續。
  • 多模型交叉檢查（Multi-Model Cross-Check）：如果可以，讓不同模型扮演不同角色。Cursor 的實驗發現，混用不同模型（規劃用能力很強的，寫程式用專精程式的）比單一模型全包更好。你的工具未必提供多種模型選項，但即使在關鍵步驟用第二個模型提供意見（例如用 GPT-4 檢查 Claude 產生的 diff），也能減少錯誤。有些開發者手動這樣做：迴路跑完後，先請 ChatGPT 審查 PR 再合併。

脈絡膨脹與最佳化

專案成長之後，要餵給代理的脈絡量可能變得很大。如果 AGENTS.md 與 progress.txt 累積到數百行，你不可能每次都全部塞進 10 萬 token 的視窗。一些建議：

  • 摘要較舊的內容：代理本身就能幫上忙。你可以提示它「摘要上面進度日誌的重點」，把摘要存起來，再截斷日誌。必要時就做摘要的摘要。這能用短得多的形式保留重要資訊。
  • 分而治之：用任務 ID 只顯示相關的日誌或程式碼片段。如果任務 7 是登入頁，提示裡就不需要購物車功能的筆記。有些自動化做法會搜尋儲存庫中與任務相關的關鍵字，只把那幾個檔案納入脈絡。
  • 善用模型既有的訓練知識：記得模型已經有大量一般知識（常見函式庫、演算法等）。除非專案用了很新或很冷門的東西，你不需要餵它可能早就「知道」的文件。例如大概不用貼整份 React 文件，只要註明「這是一個使用 Hooks 與 Vite 的 React 專案」，模型就能從訓練資料補上其餘部分。善用模型的強項，把脈絡留給專案特有的細節。

人為監督與持續改進

最後，把整套系統當成活的流程。經常監控、調整，並運用人為判斷。Ryan Carson 在建構這類迴路的經驗裡，強調調校提示與整合工作流所需的「苦工」（elbow grease）。

沒有一次到位、全自動的魔法，重點在持續微調。

你作為開發者的角色，從寫程式變成策劃流程：寫規格、審查結果、在高層次引導 AI 代理，幾乎像是你這支 AI 開發團隊的工程經理。

也要密切留意成本（API 用量）。代理卡在迴圈裡會燒掉大量 token，設定合理的上限，或許再加個預算警示。不過做對了，ROI 可以很驚人：Ralph 社群回報過產能大幅提升，也有傳聞案例是一個 5 萬美元的專案，只花了幾百美元的 API 費用就交付。

自主程式編寫代理已經來了，只要設定得當，它們能持續接手寫程式的粗活。

每一次迭代，你和代理都會變得更好。

歡迎來到 AI 強化軟體工程的下一個階段：在你睡覺時交付，讓你的代理把你的進度複利累積下去。
