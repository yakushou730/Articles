5. 統合執行狀態與業務狀態（Unify execution state and business state）

即使不在 AI 領域，很多基礎設施系統也會試著把「執行狀態」與「業務狀態」分開。在 AI 應用裡，這可能牽涉到複雜的抽象，用來追蹤目前步驟、下一步、等待狀態、重試次數等等。這樣的分離帶來複雜度，也許值得，但對你的使用情境可能殺雞用牛刀。

一如往常，什麼才適合你的應用程式由你決定。但別以為你非得分開管理它們。

講清楚一點：

  • 執行狀態：目前步驟、下一步、等待狀態、重試次數等等
  • 業務狀態：代理工作流到目前為止發生了什麼（例如 OpenAI 訊息清單、工具呼叫與結果的清單等等）

情況允許的話，簡化就對了：盡可能把兩者統合起來。

GIF 版本

實際上，你可以把應用程式設計成能從脈絡視窗推斷出所有執行狀態。很多情況下，執行狀態（目前步驟、等待狀態等）就只是關於「目前為止發生過什麼」的中繼資料。

有些東西可能沒辦法放進脈絡視窗，例如 session id、密碼相關資訊等等，但你的目標應該是讓這類東西越少越好。擁抱要素 3，你就能控制真正進入 LLM 的內容。

這個做法有幾個好處：

  1. 簡單：所有狀態只有單一真實來源
  2. 序列化：thread 可以輕鬆序列化／反序列化
  3. 除錯：完整歷史在同一個地方就能看到
  4. 彈性：新增事件型別就能輕鬆加入新狀態
  5. 恢復：載入 thread 就能從任何時間點繼續
  6. 分岔：把 thread 的某個子集複製到新的脈絡／狀態 ID，就能在任何時間點分岔
  7. 人機介面與可觀測性：把 thread 轉成人類可讀的 markdown 或豐富的網頁 UI，都很容易
